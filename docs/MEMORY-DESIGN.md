## 1 · The one-paragraph version

Decisions, notes and session observations live as **plain markdown in a central vault** — one
directory, one machine, Obsidian-readable. `amb` keeps a **derived index** of that vault in the
existing `board.db`, which is what makes it queryable across projects and injectable at session
start. Decisions never travel through the `messages` table. Repo-local copies are produced by an
explicit one-way **export**, with a staleness gate. The index is disposable: deleting it must lose
nothing.

---

## 2 · What this is not

Stated first, in this repo's convention, so it is not re-litigated.

- **Not decisions-in-the-queue.** D2 settled that: a decision has no recipient and is never
  consumed. This design depends on that split rather than eroding it.
- **Not a UI.** The vault is markdown in a directory, so Obsidian already provides graph view,
  backlinks, search, tags and mobile sync. Building a viewer would be reimplementing a better tool.
- **Not a documentation system.** Search, versioning, review and multi-year durability are git's
  job (D2's second reason). The vault can be its own git repo; the index has no independent
  lifetime.
- **Not a graph store.** No triples, no embeddings, no graph database. See §6.
- **Not automatic capture, initially.** See §9 — the automation is deliberately last.

## 3 · The tension with D2 and D16, stated

**D2 says** decisions stay in the repo they govern, because a decision is written "for a reader who
does not exist yet, who may be a human, and who may never have heard of this bus."

**This design proposes** a central vault as the authoritative home, with repo copies generated by
export.

**The argument that they reconcile:** D2's requirement is that a decision be findable by anyone who
clones the repo. Export satisfies that — the markdown lands in `docs/` and is committed. The vault
is where it is *authored and versioned*; the repo is where it is *published*.

**The argument's weak point, stated honestly:** D2's model had no failure state where a decision
exists but the repo does not have it. This one does — record centrally, forget to export, and the
repo copy silently drifts. §8's `--check` gate is what makes that acceptable. **Without the gate,
this design is worse than D2's and should be rejected.**

**D2's second reason, answered rather than conceded.** D2's scope argument ends *"git already is
that system"*, and earlier drafts of the plan simply agreed that this was the scope expansion D2
warned about. That concession is avoidable: **the vault is itself a git repository of markdown**.
Under that reading `amb` never becomes a documentation system — search, versioning, review and
multi-year durability stay git's, exactly as D2 requires, and Obsidian supplies the reading
surface. What `amb` contributes is an **index and an injector** over a documentation system that
already exists.

That reframing is falsifiable, which is what makes it worth stating: if building this ever
requires `amb` to grow its own search, revision history or viewer, D2's second reason has won and
the design was wrong. §2's "not a UI" and "not a documentation system" are the same commitment,
stated as boundaries; this states it as the argument.

**D16 is the sharper conflict.** It rejects `amb promote` on the grounds that a command "would
create a mechanism that looks authoritative while checking the part that matters not at all."
The promotion pipeline in the plan's Phase 2 is a different mechanism with the same verb, and the
distinction has to be made explicitly rather than assumed:

- D16's `promote` moved a *foreign finding* into a repo, claiming validation against a tree the
  command could not inspect.
- Phase 2's promotion moves a *candidate* to a *decision* inside the vault, on evidence the
  command can inspect (a derivation ledger), with the user approving.

That may be a real distinction or it may be a rationalisation. It is Q10's central question, and
the answer decides whether Phase 2 exists at all.

**A third kind of traffic that D2's table does not cover.** Session observations are neither
messages nor decisions: they are unaddressed like a decision, but they expire like a claim, and
D11 forbids writing them inside a repo. The vault is the only place they can live.

| Traffic | Lifecycle | Home |
|---|---|---|
| Direct message / broadcast | consumed once | bus |
| Claim | expires | bus |
| **Session observation** | **decays** | **vault** (`projects/<name>/`) |
| **Candidate** | expires unless promoted | **vault** (`candidates/`) |
| **Capture** | kept, never injected | **vault** (`captures/<project>/`) (D86) |
| **Decision** | never consumed | **vault**, exported to repo |

## 4 · Storage model

**The vault is truth. The index is derived.** The test, and it must stay true:

```
rm ~/.agent-messageboard/board.db   →  loses zero notes
```

If that ever stops holding, the design has drifted into D2's rejected shape — a competing home for
the decision.

```
~/vault/                                    # configurable; default points where a human
├── projects/<name>/<date>-<slug>.md        # would naturally open Obsidian, NOT inside
├── candidates/<slug>.md                    # ~/.agent-messageboard/
├── decisions/<project>/<slug>.md           # a decision scoped to one project
├── topics/<topic>/<slug>.md                # a decision scoped to a topic  (D82)
├── global/<slug>.md                        # a decision scoped everywhere  (D81)
└── captures/<project>/<slug>.md            # machine-written failure scrollback; searchable,
                                            # never injected                (D86)
```

**The directory *is* the scope, written out for a human** (D81). Someone browsing this in Obsidian
sees `topics/rust/` and `global/` and knows what they are looking at without opening anything. The
sigils that spell a scope in an id — `#rust`, `@@` — deliberately stay out of path names: both are
legal in a filename and hostile in a shell, and this is the one place the grammar buys nothing.

> **Was `patterns/<slug>.md` until D81.** A "pattern" was a decision that applied everywhere, with
> the scope smuggled inside the kind; `global/` is the same notes under a name that says what they
> are. There is no migration for the files because none existed on disk.

**One file per observation.** An earlier draft used a single append-only
`projects/<name>/observations.md`. Three things break on that, and all three are invisible until
the index in §5 is written down: every project's file has the stem `observations`, so they collide
on a `(kind, slug)` key; an individual observation has no identity for "inject the last N", for
FTS5, or for the citation ledger to name; and rebuilding a disposable index from an append-only
blob requires a stable in-file anchor that does not exist. Separate files supply the anchor for
free, and Obsidian prefers many small notes regardless.

**Vault and index have opposite sync requirements, which is the reason to keep them separate.**
Plain markdown syncs across machines safely — iCloud, Dropbox, git, anything. A SQLite index does
not: D15 already refuses synced volumes because the locking primitives are not reliably honoured
there. So the vault may sync; the index rebuilds locally per machine.

`[[wikilinks]]` cost nothing to emit and Obsidian resolves them for free. Whether `amb` writes them
or leaves linking to the human is open (§12).

## 5 · Schema

Three tables in the existing `board.db` (D15), sharing the pragmas and `BEGIN IMMEDIATE`
discipline in `DESIGN.md` §Storage. One database means one open path, one sync-root guard, one
concurrency configuration.

**They arrive as a migration step, not as new DDL in `schema.sql`.** The board carries a ladder
keyed on `PRAGMA user_version`, applied in a single transaction; these tables are step **2 → 3**
and are additive, which is the ladder's stated precondition. Note also that `foreign_keys` is now
`ON`, so the foreign key below is **enforced** — that is why it and `notes` must agree on
`(kind, scope, slug)`, and why the earlier mismatch was a defect rather than a tidiness issue.

Content is **not** stored — only what is needed to find the file and judge it. `body_excerpt` is a
display convenience, capped, never the authority — and until D88 it was also what `recall` matched
against, which made "capped" mean "most of every note was unsearchable". Free-text recall now
narrows on this index and reads the *file* to decide, so the excerpt is a display convenience in
fact and not only in intent.

```sql
CREATE TABLE notes (
  slug         TEXT NOT NULL,        -- file stem; stable identity, and it carries the date
  kind         TEXT NOT NULL,        -- observation | candidate | decision | capture  (D81, D86)
                                     -- `capture` is machine-written and excluded from
                                     -- INJECTABLE; `candidate` from both INJECTABLE and
                                     -- SEARCHABLE. Every kind sits in exactly one side of each
                                     -- partition, asserted rather than counted (D86).
  -- **Where the note applies, on its own axis** (D81). `address::Scope`'s stored form: a bare
  -- project id, `#topic`, or `@@`. Was `project`, which meant a project *and* -- through the
  -- `pattern` kind -- meant "everywhere"; that encoding survived exactly two scopes.
  -- NOT NULL, and a candidate carries '' rather than NULL. SQLite -- alone among SQL engines --
  -- permits NULLs in a PRIMARY KEY and does not compare them equal, so a nullable column would
  -- have let two rows share a key and silently defeated the upsert.
  scope        TEXT NOT NULL,
  vault_path   TEXT NOT NULL,        -- relative to vault root; cite this, never a line number
  title        TEXT NOT NULL,
  status       TEXT NOT NULL,        -- active | promoted | superseded | expired
  derived_count INTEGER NOT NULL DEFAULT 0,   -- candidates only; mirrors frontmatter
  body_excerpt TEXT,
  created      REAL NOT NULL,        -- added in the build: ordering by recency needs the note's
                                     -- own date, not the file's mtime, which a sync client moves
  -- **`content_hash` was here and is gone** (D85). It was written on every index pass and read by
  -- nothing; an earlier comment called it "change detection; the whole freshness story", which was
  -- false — `sync_dir` decides the skip on `mtime` alone and returned before this column was ever
  -- looked at. Believing that sentence produced a migration that could not take effect (D67).
  -- Confirming a change by hash means reading the file, which is what the `mtime` gate exists to
  -- avoid, so the second stage it might have become could never pay for itself.
  mtime        REAL NOT NULL,        -- the *only* gate. Invalidating index state means clearing
                                     -- this, never a derived column (D67)
  indexed_at   REAL NOT NULL,
  force        TEXT NOT NULL DEFAULT 'advice',  -- advice | decision | rule. Ranks a note ahead of
                                     -- others under the injection cap; never denies anything
                                     -- (D52, D64)
  -- `scope` is part of the key, not merely an attribute: two projects may legitimately hold
  -- notes with the same slug, and an earlier draft's `PRIMARY KEY (kind, slug)` silently
  -- collapsed them.
  PRIMARY KEY (kind, scope, slug)
);
CREATE INDEX ix_notes_scope ON notes(scope, kind, status);

-- Which files a note claims to concern. The primary retrieval key (§6).
CREATE TABLE note_paths (
  kind      TEXT NOT NULL,
  slug      TEXT NOT NULL,
  scope     TEXT NOT NULL,           -- the note's scope; part of its identity
  path_glob TEXT NOT NULL,           -- repo-relative, as authored
  PRIMARY KEY (kind, scope, slug, path_glob),
  -- Was `REFERENCES notes(kind, slug)` while this table keyed on the scope column too — a foreign
  -- key narrower than the table referencing it. Both now agree on (kind, scope, slug).
  FOREIGN KEY (kind, scope, slug) REFERENCES notes(kind, scope, slug) ON DELETE CASCADE
);
CREATE INDEX ix_note_path ON note_paths(path_glob);

-- The one relationship the vault has, made queryable (D63). Derived from frontmatter and rebuilt
-- on every index pass exactly as `note_paths` is, so `rm board.db` still loses zero notes.
CREATE TABLE note_links (
  kind    TEXT NOT NULL,
  scope   TEXT NOT NULL,
  slug    TEXT NOT NULL,
  rel     TEXT NOT NULL,             -- only `superseded_by` so far; the vault needs far fewer
                                     -- link types than the published vocabularies offer
  target  TEXT NOT NULL,             -- text, not a foreign key: a target may legitimately not
                                     -- exist, and dangling is something to *report* rather than
                                     -- to make unrepresentable
  PRIMARY KEY (kind, scope, slug, rel, target)
);
CREATE INDEX ix_note_links_target ON note_links(target, rel);
```

**`derived_count` is mirrored, not owned.** The authoritative ledger lives in the candidate's
frontmatter (plan, Phase 2), so that deleting the index does not destroy promotion evidence. Where
the two disagree, **the file wins** — disk outranks status.

**The citation ledger — the third table, and the one that makes the receipts arithmetic.**

```sql
-- What each session was shown, and what it later admitted using. Two counters, no judgement.
CREATE TABLE note_events (
  session   TEXT NOT NULL,           -- CLAUDE_CODE_SESSION_ID, as everywhere else
  kind      TEXT NOT NULL,
  scope     TEXT NOT NULL,           -- denormalised, like `force`: the scope at the moment of the
                                     -- event, so a note that is later re-scoped does not
                                     -- re-attribute its own history (D81)
  slug      TEXT NOT NULL,
  -- As built: injected | injected_file | cited. `injected_file` is the PreToolUse path, kept out
  -- of the divided number because its delivery to a model is unverified (D42).
  --
  -- **Only the two `injected*` rows are exposure.** D59's window is bounded by them and not by
  -- any row in this table, because a `cited` event can be produced by hand — dating a measurement
  -- from one would put the implementer's own bookkeeping inside it (D79).
  --
  -- **The window itself lives in `measurement_window`, not here** (D87). It has to be stored
  -- somewhere: `receipt` always took a `since`, but the only caller-facing control was
  -- `--days N` — days back from *now* — so a fixed start was unsayable and the default was all
  -- time, which counted events D79 had excluded.
  event     TEXT NOT NULL,
  ts        REAL NOT NULL,
  force     TEXT NOT NULL DEFAULT 'advice',   -- likewise denormalised, and for the same reason
  PRIMARY KEY (session, kind, scope, slug, event)
);
CREATE INDEX ix_note_events_slug ON note_events(kind, scope, slug, event);
```

This is derived state and belongs in the index rather than the vault: it describes *sessions*,
which are ephemeral, not *notes*, which are durable. Losing it to `rm board.db` costs a
measurement, not a note — consistent with §4.

> **"Derived" is the wrong word for it, and D81's migration is where that showed.** Nothing
> regenerates this table: no file records that a session was shown a note. So when 8 → 9 dropped
> and rebuilt `notes`, `note_paths` and `note_links` from the vault, `note_events` had to be
> carried across row by row instead. It is *disposable* in the sense §4 means — losing it costs a
> measurement, not a note — and it is not *rebuildable*, which is a different property that only
> matters on the day something rewrites the schema.

It answers three questions no self-report can:

- **Phase 1's receipt:** `count(cited) / count(injected)`. Zero means injection is not working and
  nothing further gets built.
- **Phase 2's independence test:** a derivation is independent only when nothing injected into that
  session concerned the same paths. Without this table that rule is unenforceable — see the plan's
  Phase 2, where the earlier "independent by construction" claim is corrected.
- **Retirement:** if no note older than N days is ever cited, N is the expiry (§12).

**`injected` rows are written by the read path**, which means `SessionStart` performs a write.
That is a real cost and must be measured (§13) — it is one small `INSERT` batch against a database
already open, but the hook budget is shared with mail delivery (§11).

**The window the receipt is computed over — the fourth table, and the smallest one.**

```sql
-- When a measurement started. Named, because Q10's cross-repo arm is documented as needing its
-- own date and its own decision, so a second window is a future need rather than speculation.
CREATE TABLE measurement_window (
  name      TEXT PRIMARY KEY,     -- 'injection' is D59's; there is one today
  opened_at REAL NOT NULL
);
```

**Why this is a table and not a flag** (D87). `receipt` always took a `since`, but the only
caller-facing control was `amb memory status --days N` — an integer count of days back from *now*
— so a fixed instant could not be named and the default was all time. D59's floor and D79's start
date were therefore prose that nothing could evaluate, and the printed ratio covered events D79 had
excluded. On the board this was written against that included a hand-run probe session which wrote
8 injections, could never cite anything, and was 14% of the denominator.

It sits on the board rather than in the vault for the same reason `note_events` does, and the two
are meaningless apart: a window is a range over that ledger, so losing the board loses a
measurement that was already lost rather than stranding a date pointing at events that are gone.

**Whether recall was reached for at all — the fifth table** (D89).

```sql
-- One row per search, never per note. `INTEGER PRIMARY KEY` is a surrogate that deduplicates
-- NOTHING, and that is the design: the cheaper move, a sentinel row in `note_events`, inherits
-- PRIMARY KEY (session, kind, scope, slug, event), so five searches in one session would record
-- one row -- a denominator counting distinct things rather than times the cost was paid.
CREATE TABLE searches (
  id           INTEGER PRIMARY KEY,
  session      TEXT NOT NULL,
  ts           REAL NOT NULL,      -- so D87's window scopes it like everything else on the receipt
  lane         TEXT NOT NULL,      -- text | path | across
  hits         INTEGER NOT NULL,
  foreign_hits INTEGER NOT NULL DEFAULT 0   -- Q10's differentiator, counted where it fires (D91)
);
```

**No query text is stored.** The receipt asks *was recall reached for* and *did it find anything*;
`lane` and `hits` answer both. A query is agent-written text that can carry a secret — the vault
redacts for exactly that reason — and collecting search terms would create a surface to protect in
order to answer a question nobody asked.

**Why it exists.** `unprompted` counts citations of notes a session was never shown, which it can
only have reached through `recall`. Nothing recorded that recall ran, so `unprompted: 0` meant
either *no session wanted a note it had not been given* or *sessions asked and the search lost the
answer* — and D59 retires the injection layer partly on the first. D88 established that the second
was happening: recall matched a 240-character slice of each note's first paragraph, so a lesson
written after a blank line answered `no notes match`.

`foreign_hits` is the same correction applied to Q10. `cross_repo_query` counted invocations of
`recall --file --across-repos`, a flag named in no README, no primer and no banner, while
`across_repos` merely re-sorts `concerning` — so the capability fired through the documented path
and the counter never saw it (D91).

## 6 · Retrieval — path anchoring primary

**Path anchoring is primary; full-text is secondary.** The query that matters is *given the file I
am about to touch, what do I know that concerns it, here or in any other project?* That is a glob
join on `note_paths`, the same shape as the existing claims lookup.

**The evidence, and its limit.** A sibling project measured prose full-text search across five
field runs and found it **never uniquely converted** — every document it surfaced was also surfaced
by path anchoring — and demoted it to a supplement. That receipt is **borrowed, not earned here**,
and it covers *decisions* only.

It does **not** transfer to session observations. "The session where we fought the flaky fixture"
is a semantic query with no shared keywords, and path anchoring will miss it. So:

- **Decisions and candidates:** path anchoring, FTS5 as supplement.
- **Observations:** FTS5 matters more, and this is the weakest-evidenced part of the design.

**Whether path anchoring can work at all is now measurable, and it is a precondition for judging
whether it does.** `amb memory coverage` reports how many of the files sessions actually edit are
covered by any note (D66). Path-anchored injection that never fires because coverage is near zero
is not evidence against path anchoring — it is evidence there was nothing to anchor to, and the
two are indistinguishable in the receipt. First real reading: 7 of 24 edited paths in this repo,
and **0 of 7 in a second project whose notes name two files no session has ever opened.**

SQLite's FTS5 is a table and a trigger away if the receipt is re-earned here, and **the incumbent
proves the shape at scale**: claude-mem runs FTS5 external-content tables
(`content='observations', content_rowid='id'`) kept in sync by `AFTER INSERT` / `AFTER DELETE` /
`AFTER UPDATE` triggers, over **80,264 rows**. That is the exact pattern to copy — external
content means the index stores no second copy of the text, which matters when the authority is a
file on disk rather than a column.

**Their dedup key is the lesson in the negative.** `observations` carries a `content_hash` with a
unique index on `(memory_session_id, content_hash)` — scoped to one session. Across the whole
corpus, **80,264 rows hold 80,264 distinct hashes**: a repeat in a later session is not a
duplicate, so cross-session dedup has never fired once. Any hash key here must be scoped to
`(kind, scope, slug)` and not to a session, or it is decoration.

Vector search is out of scope (§10).

## 7 · Trust — cross-repo is the shared-root case, by default

The hardest-won lesson available, and it must ship in v1 rather than after an incident.

A sibling project shipped provenance *attribution* for memory imported from outside the local tree,
concluded attribution alone was insufficient, and followed it with a **trust tier**: foreign
documents may advise, never coerce, unless coercion is explicitly granted. It then shipped a second
coercive surface three releases later that **bypassed its own tier** — same defect, new door.

Here every cross-project result is that case, and it is the default rather than an opt-in.

- A note from the caller's own project is **local**.
- A note from any other project is **foreign**, and every surface that renders it says so —
  `[nestwatch] auth-lock-ordering` — with no exception and no quiet path.
- **Foreign notes are advisory only.** They inform; they never gate, block or deny. If a gating
  surface is ever added, foreign notes are excluded **by construction**, not by a config flag a
  later feature can forget to read.
- The reason is D16's own: only a session working in a repo can validate against that tree. An
  index cannot, and must not imply it did.

**Patterns are the deliberate exception** — a promoted cross-project principle is authored by the
user, not imported, so it is local everywhere. That exception exists because the promotion gate is
what earns it.

## 8 · Export and the staleness gate

**One direction: vault → repo. Never back.**

`amb memory export <project>` writes `docs/decisions/` in that repo, each file carrying a
generated-by header naming the vault path it came from. The user commits them, so D2's reader who
clones the repo finds them.

`amb memory export --check` exits non-zero when a repo's exported copy differs from the vault.
**This is not optional** — it is the entire answer to §3's weak point. Wire it into CI or a
pre-commit hook and drift becomes a detected failure rather than silent decay.

Two disciplines borrowed from devt's field arc:

- **No export ships a placeholder.** Hard-fail (exit 2, token named) on any unsubstituted
  `{snake_case_token}` in a rendered file. devt's version of this check caught a real defect in its
  own fixtures the day it shipped.
- **`--check` compares content hashes**, never an `exported_at` timestamp field. A status field can
  lie; the file cannot.

Whether export is per-decision opt-in (`scope: project` frontmatter) or dumps everything tagged
with the project is open (§12). The lean is opt-in: a personal principle derived partly inside an
employer's repo should not auto-publish there.

## 9 · Session memory, and the claude-mem question

### 9.1 The mechanism

The blocker for replacing claude-mem was always semantic compression: raw tool-call capture is
deterministic and easy, but turning 347 tool calls into *"fixed a race in auth by moving lock
acquisition earlier"* is summarization, and no regex writes that sentence. claude-mem solves it
with a **background worker on a local port** (`CLAUDE_MEM_WORKER_PORT`, 37701 on this
machine) making separate agent-sdk calls — an architecture
unavailable here, because D3 rejected broker daemons and an LLM on the write path destroys both
determinism and the startup cost that justified Rust.

> **Correction, measured 2026-08-27 against `amb 0.1.0` release.** Earlier drafts cited "the
> 1.31 ms startup that justified Rust". That figure is `/bin/echo` — `MEASUREMENTS.md` names it a
> deliberately optimistic stand-in for "a small native binary", from before this binary existed.
> The real numbers, 50 runs, median, repeated twice: **`amb --version` 2.0 / 2.2 ms**, **`amb
> inbox` 3.2 / 3.5 ms**, against `python3 -c pass` at 16.6 / 17.5 ms. The conclusion is unchanged
> — a full inbox check still finishes before Python reaches its first statement — but the margin
> is ~8x on bare startup and ~5x doing real work, not 15x. It matters here because injection
> spends from the same hook budget (§11).

**The third path:** a `Stop` hook can return `{"decision": "block", "reason": "…"}`, and the
harness feeds that reason back to Claude as its next instruction — the turn continues instead of
ending. The hook does not compress anything; it asks the session to summarize itself, and the
session already holds the context.

Why that is better here than claude-mem's shape:

- **No worker process.** D3 holds.
- **No second API key and no separate per-session billing.** It rides the session already running.
- **Better raw material.** claude-mem's worker reconstructs meaning from extracted observations;
  the session knows *why*, not just *what*.
- **Unprompted by construction.** `Stop` fires at every turn end regardless of whether any ritual
  ran — which is the gap that keeps ritual-bound memory systems empty.

The `Stop` hook also receives **`transcript_path`**, the session's own JSONL on disk, so
deterministic fact extraction needs no capture hook at all.

> **Verify before building — and a first pass already found discrepancies.** These hook fields
> came from a mix of the official reference and third-party guides. Re-checked **2026-08-27**
> against <https://code.claude.com/docs/en/hooks>: `stop_hook_active` is not listed among `Stop`'s
> inputs, blocking is documented as **exit code 2**, and the reference explicitly says hooks
> needing the final assistant text should use **`last_assistant_message` instead of reading the
> transcript**. The surface is ~31 events and moves, so re-check again at build time rather than
> trusting this paragraph. See the plan's Phase 4 for the probe that settles it, and note that
> **`PreCompact` is a better trigger than the turn threshold described below** — it fires exactly
> when context is about to be lost.

### 9.2 The two non-negotiables

- **The re-entry guard is checked on the first line, always** — whatever it turns out to be
  called. The requirement is absolute: a hook that blocks must be able to tell that it is already
  inside a forced continuation, or the session can never end. **The mechanism is not confirmed.**
  Earlier drafts named `stop_hook_active`; a re-check of the hooks reference on **2026-08-27**
  does not list it among `Stop`'s inputs (`session_id`, `prompt_id`, `transcript_path`, `cwd`,
  `permission_mode`, `effort`, `hook_event_name`, `last_assistant_message`), and documents
  blocking as **exit code 2** rather than the `{"decision":"block"}` shape cited in §9.1. A
  non-negotiable resting on a field that may not exist is not a safety mechanism — settle it with
  a first-hand probe, the way Q7 was settled into D25, before any of this is built. The plan's
  Phase 4 carries the gate.
- **Redaction ships before any automated capture.** `<private>` exclusion plus a secret-shaped
  filter, applied on the write path. Everything captured eventually reaches a model, so a memory
  store that swallows secrets is worse than no memory store.


> **Settled 2026-08-28, from the reference read in full.** Blocking `Stop` is **exit code 2**, not
> a `decision` field — *"Prevents Claude from stopping, continues the conversation"*. The summary
> must come from `last_assistant_message` rather than `transcript_path`, and the reason is
> correctness rather than convenience: the transcript *"is written asynchronously and may lag the
> in-memory conversation"*, so it may not contain the turn a hook is firing on. And **neither
> compaction event can inject** — `PreCompact` can only block, `PostCompact` can do neither — so
> the re-injection point is `SessionStart` with `matcher: "compact"`, which Phase 1's hook already
> fires on.
>
> **The load-bearing one is now settled: `stop_hook_active` exists.** Absent from the reference on
> two full readings, then observed as **`true`** in a live `Stop` payload — delivered to a hook that
> blocks and continues the conversation, so the session was in exactly the re-entry state the field
> names. **The requirement below can name its mechanism**, and §11's infinite-loop risk is
> mitigated rather than open. Provenance and its limits: `MEASUREMENTS.md` M10.
>
> A blocking `Stop` hook must therefore read `stop_hook_active` on its first line and return
> immediately when it is true. Not a convention — the only thing between this design and a session
> that cannot end.

### 9.4 Injection discipline

Two rules borrowed from devt, both earned by field defects:

- **Scope the injection to the consumer.** devt found five parallel reviewers writing near-identical
  explain-aways of the same two global documents, because everyone got everything. Inject what
  concerns the caller's files, not the whole recent history.
- **Empty is not broken.** A bare `{}` is reserved for "the vault is genuinely unavailable". When
  nothing matches, inject a one-line checkable claim — *"no prior observations for this project"* —
  or every agent burns a turn checking whether memory is down.

## 10 · What is genuinely lost versus claude-mem

- **Vector search.** Lexical only. Defensible for decisions; **the weakest point of the design for
  observations** (§6). **What it saves, measured on the incumbent 2026-08-27:** its Chroma store is
  **3.0 GB against a 570 MB database** — the vectors are more than five times the size of
  everything they index. That is the price of the capability, and it is worth knowing before
  calling the loss acceptable.
- **Maturity.** A large user base finding edge cases, against a fresh implementation with none.
- **Multi-IDE**, the **web viewer**, and compression prompts tuned across many users' sessions.
- **Turn-level granularity.** Threshold-triggered summaries are coarser than continuous
  observation. Probably fine; unproven.

**Migration:** do not build an importer for v1. Episodic memory has a short half-life. Run both in
parallel for a few weeks and compare what each surfaces at session start — that comparison is the
receipt that decides whether to uninstall.

## 11 · Risks

| Risk | Mitigation |
|---|---|
| **Memory degrades or breaks mail delivery** — the `Stop` hook that would block for compression is the *same* hook that delivers mail, under one shared 5 s `HOOK_TIMEOUT_SECS`, and D9 requires delivery never break a session | **Delivery emits first and is never downstream of memory work; memory's contribution is separately bounded and fails soft; hook-safety tests extended to cover a memory layer that hangs, panics or returns garbage — not only one that is absent.** The failure shape is an empty inbox, which is this project's documented worst case |
| Infinite `Stop` loop | **Mitigated, 2026-08-28.** `stop_hook_active`, read on the hook's first line, returning immediately when true. Undocumented but observed `true` in a live payload during an actual re-entry (`MEASUREMENTS.md` M10). Because it is undocumented, a `Stop` hook must also fail closed if the field is *absent* — treat missing as "cannot prove this is not re-entry" and decline to block |
| Intrusiveness — blocking mid-flow | Threshold-trigger; test `--append-system-prompt` as the non-blocking alternative first |
| Token cost (injection is a permanent tax) | Cap injection; measure bytes injected against how often they are cited; delete the feature if never cited |
| Summary quality | The session may write lazy summaries of its own work. **Prototype in shell before any Rust** |
| Secrets captured | §9.2 |
| Transcript format drift | Internal format, no compatibility promise. Parse defensively, fail soft |
| Export drift | §8 `--check` |
| Scope bloat | `amb` becomes four concerns in one binary — and **D27 has since narrowed what `amb` claims to be**, so this now argues against a deliberately tightened definition. Keep every layer independently disableable; note that the kill-switch has no home yet, because there is **no config file** (§12) |
| Hardening a directory the user owns | The vault is chosen by the user and may be a git repo or sync root. **D31 applies**: narrow a directory only when this open created it. `amb` writes files into the vault and never changes its mode |

## 12 · Open questions

**The retrieval trace records what was shown, not what triggered it.** Surveyed against 2026
practice on **2026-08-28**: a provenance-aware trace is expected to record *the triggering query or
context* alongside the items retrieved and the downstream links. `note_events` records the session,
the note, and whether the injection came from recency or from a path — but not *which* path. So
"this note was cited" is answerable and "notes about `src/auth` get cited, notes about `src/ui`
never do" is not.

Deliberately not built yet. It is a schema change in service of an analysis the ledger has no data
for, and building the answer before the measurement is the failure this whole plan is arranged to
avoid. Revisit when the receipt is non-zero.

**The index cannot filter by author or session.** Both are in the frontmatter and neither is a
column, so "show me only what *I* recorded" is unanswerable. The same practice survey treats
separating agent-generated inferences from user-stated facts as a retrieval-time filter. Cheap to
add; no evidence yet that it is wanted.



**Q10 governs §7 and §8, not §4–§6.** Whether the central vault reconciles with D2 and D16 is a
question about *decisions* and *promotion*. Session observations are a traffic type neither
decision covers, so the observations layer is buildable while Q10 stays open (§3, and the plan's
*What Q10 actually governs*). Earlier drafts said "Q10 governs all of this"; that was the single
most costly error in this file, because it gated the cheap experiment behind the expensive
argument.

~~**Dedup for derivations.**~~ **Answered.** It becomes an affordance rather than an algorithm:
at `observe` time, show the candidates already concerning those paths — a free query, since
retrieval is path-anchored — and let the caller echo an id. A miss then produces a visible
duplicate rather than a silent wrong merge, and the echo is exactly the derivation evidence the
plan's Phase 2 needs. A near-match shown this way is itself an injection and is recorded as one.

**Does `amb` write `[[wikilinks]]`,** or emit plain text and leave linking to the human?

**Is export per-decision opt-in or project-wide?** (§8)

~~**Do observations expire?**~~ **Answerable, not guessable.** The citation ledger (§5) makes this
empirical: if no note older than N days is ever cited, N is the expiry. Do not pick a number
before the data exists.

**Should this be a second binary** sharing the vault directory but not the database? Cheaper to
reason about; one more thing to install. One argument against the split, not previously stated:
a second binary must also write `~/.claude/settings.json`, since memory needs `SessionStart` and
`Stop`. That is the file `CLAUDE.md` singles out as the one whose corruption "breaks the user's
whole tool, not just this one", and two installers contending over it is a worse failure than one
binary with a per-layer kill-switch. It would also duplicate identity resolution, project
resolution and the sync-root guard.

**Is lexical-only recall enough for observations?** (§6) Unchanged and still the weakest-evidenced
part of the design — but now measurable rather than arguable, since the ledger records what was
shown as well as what was used. A low cite rate with good coverage is a retrieval failure, not a
memory failure, and the two were previously indistinguishable.

## 13 · What must be measured before believing any of this

Nothing above is measured. In this repo's convention, that makes all of it judgement.

1. **Does injected memory change an action?** The standing test, and now an arithmetic one:
   `count(cited) / count(injected)` from `note_events` (§5), over two weeks of real sessions. If
   the ratio is zero the whole design is answered cheaply, nothing else gets built, and Q10 never
   needs settling. A ratio near zero with a *large* denominator is the distinct and more useful
   failure: injection works and is noise — fix retrieval, not memory. **Read `amb memory coverage`
   before concluding either** (D66): a zero ratio over low coverage means path anchoring had
   nothing to inject, which calls for more notes rather than fewer hooks, and the receipt alone
   cannot tell that from noise.
2. **Are self-written summaries usable?** Prototype the `Stop`-block in a shell script against a
   live session and read what it produces. If they are vague, the design collapses to deterministic
   facts only — still useful, different project.
3. **Is lexical-only recall enough for observations?** Run real "which session did X" queries
   against FTS5. This decides whether the vector-search loss is acceptable.
4. **Index cost**, cold and warm, for a vault of N notes.
5. **Token cost** in both directions: summarization and injection.
6. **Is the cross-project query ever run?** If not, the differentiator is dead weight and this
   shrinks to a local index — or to nothing, since `rg` already searches one directory.
